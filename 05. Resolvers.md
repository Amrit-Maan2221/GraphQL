# 1️⃣ What a Resolver Really Is

> A **resolver is a function that tells GraphQL how to fetch or compute the data for a specific field.**

Think of it like this:

* Schema = the **contract** (what fields exist, types, relationships)
* Query/Mutation = the **request** (what the client wants)
* Resolver = the **implementation** (how the server actually delivers the data)

Without resolvers:

* The schema exists
* Queries fail → “I don’t know how to get this data”

---

# 2️⃣ Resolver Basics

Every field in a schema **can have a resolver**.

Example schema:

```graphql
type User {
  id: ID!
  name: String!
  vehicles: [Vehicle]
}

type Vehicle {
  plateNumber: String!
  model: String
}
```

**Query:**

```graphql
query {
  user(id: 101) {
    name
    vehicles {
      plateNumber
    }
  }
}
```

**Resolvers (pseudocode):**

```csharp
UserResolver(parent, args, context) {
    // args.id = 101
    return DB.Users.Find(args.id)
}

VehiclesResolver(parent, args, context) {
    // parent = user object returned from UserResolver
    return DB.Vehicles.Where(v => v.UserId == parent.Id).ToList()
}
```

✅ Key insight: **Resolvers run per field**, not per object.

---

# 3️⃣ Parent / Child Relationships

* The `parent` argument is the **previous object in the hierarchy**
* This allows **nested queries** to work naturally

Example:

```graphql
query {
  user(id: 101) {
    name
    vehicles {
      plateNumber
    }
  }
}
```

* `UserResolver` → returns `{ id: 101, name: "Amrit" }`
* `VehiclesResolver(parent)` → parent = `{ id: 101 }` → fetch vehicles for that user

> Senior tip: Always leverage `parent` to avoid unnecessary DB calls.

---

# 4️⃣ Arguments & Context

Every resolver usually has:

```text
resolver(parent, args, context, info)
```

* `parent` → previous level data
* `args` → field arguments (e.g., id, input object)
* `context` → global info (user session, auth token, DB connections)
* `info` → query metadata (rarely used, for advanced stuff)

✅ Senior insight: **context is your secret weapon** for auth, caching, and multi-tenant systems.

---

# 5️⃣ N+1 Problem & Batching

Naive resolvers:

```csharp
vehicles = users.map(user => DB.Vehicles.Where(v => v.UserId == user.Id))
```

* DB query runs **once per user** → N+1 problem

Solution:

* **Batch requests**
* Use tools like **DataLoader** (or implement your own caching/batching)

> Senior mantra: Every resolver must be **efficient**, especially nested ones.

---

# 6️⃣ Mutation Resolvers

Mutations work the same way, but you also **write to DB**:

```csharp
CreateUserResolver(parent, args, context) {
    user = new User { Name = args.input.name, Email = args.input.email }
    DB.Users.Add(user)
    DB.SaveChanges()
    return user
}
```

* Always return **exact object required** by the frontend query
* Wrap multiple DB operations in **transactions** if needed

---

# 7️⃣ Advanced Resolver Patterns

1. **Resolver Composition**

   * Reuse resolvers for different fields

2. **Field-Level Security**

   * Check permissions inside resolver, not in schema

3. **Error Handling**

   * Throw errors inside resolver → GraphQL adds them to `errors` array
   * Never return `null` silently if something is wrong

4. **Caching**

   * Cache field results in context / Redis / memory for repeated calls

---

# 8️⃣ Senior TL;DR

* **Resolvers = GraphQL’s execution engine**
* Runs **per field**, not per query
* `parent` lets you navigate relationships efficiently
* `args` = dynamic field input
* `context` = global info (auth, DB, multi-tenant)
* Avoid N+1 → batch DB calls
* Mutation resolvers handle writes + return exactly requested data

> Senior mindset: Queries & Mutations are **contracts**, resolvers are **where your architecture actually matters**.
