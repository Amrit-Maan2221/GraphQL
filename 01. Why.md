## Why GraphQL Exists

To understand GraphQL, you have to understand what it was designed to fix in REST APIs.

### The overfetching problem

A REST endpoint returns a fixed shape. If a client asks for a user's name, a typical `/users/101` endpoint might return the full user object — email, address, preferences, timestamps, everything — even though only the name was needed.

At low volume this is a non-issue. At scale, it adds up: wasted bandwidth, worse mobile latency, extra serialization work, and higher infrastructure cost.

### The underfetching problem

The opposite issue is arguably worse. A single screen often needs data that spans several resources — say, a user, their orders, their vehicles, and their support tickets. In REST, that's typically four separate requests:

```
/user/101
/user/101/orders
/user/101/vehicles
/user/101/tickets
```

This is often called a "chatty" API, and it's a real problem on mobile networks: more round trips means slower UI and worse battery life.

### The versioning problem

Frontend teams tend to ship faster than backend teams — mobile and web iterate quickly, while backend APIs are usually more conservative and tightly controlled. Every time the UI needs a new field, it has to go back to the backend team, and the common fallback is versioning:

```
/v2/user
/v3/user
```

Multiple API versions accumulate, and maintaining all of them becomes its own long-term burden.

### Facebook's context

These problems compounded at Facebook, which had to serve web, iOS, and Android clients — including users on slow 3G connections — from the same backend. They needed a way to fetch exactly the right data in a single request, without the client being tied to a rigid, versioned schema. That work became GraphQL, developed internally starting in 2012 and released publicly in 2015.

### The core idea

The defining shift is this: **the client specifies what it needs, and the server fulfills exactly that** — not the other way around.

```graphql
query {
  user(id: 101) {
    name
    vehicles {
      plateNumber
    }
  }
}
```

```json
{
  "data": {
    "user": {
      "name": "Amrit",
      "vehicles": [{ "plateNumber": "ABC123" }]
    }
  }
}
```

One request, no extra fields, no unused data.

### It's not really about bandwidth

A common misconception is that GraphQL's main benefit is "sending less data." The more important benefit is **schema evolution without versioning**. Because clients declare which fields they want, existing clients keep working unchanged when new fields are added — there's rarely a need for `/v2` or `/v3`. For large, long-lived APIs, this is a significant advantage over REST's versioning treadmill.

### GraphQL as an aggregation layer

As systems move to microservices — say, separate User, Workshop, Billing, and Notification services — the frontend often needs data assembled from several of them at once. Without GraphQL, this typically means building a Backend-for-Frontend (BFF) layer with a growing number of aggregation endpoints, which gets messy fast.

GraphQL naturally fills this role: a single query can pull from multiple underlying services, giving the client one clean interface instead of many purpose-built endpoints.

### When GraphQL is the wrong choice

GraphQL isn't a universal upgrade over REST. It tends to be a poor fit when:

- **The system is simple CRUD** — internal tools and admin panels are usually faster to build with plain REST.
- **The workload is write-heavy** — GraphQL's strengths are mostly on the read side; mutations are often more complex to design well than equivalent REST endpoints.
- **Caching matters a lot** — REST's `GET /users/101` caches easily at the CDN level. GraphQL typically sends queries via `POST /graphql`, where every request can differ, requiring more deliberate caching strategies.
- **The team lacks GraphQL experience** — poorly implemented resolvers are a classic source of N+1 query problems that can quietly overload a database. Avoiding this requires deliberate use of techniques like DataLoader-style batching, which adds real engineering overhead.

### The real takeaway

GraphQL's biggest value isn't technical efficiency — it's organizational. It gives frontend teams more autonomy, reduces the need for coordinated backend releases, cuts down on breaking changes, and supports schema-driven development across multiple client types. That's the actual reason large companies adopt it — not because it's trendy, but because it changes how frontend and backend teams can work independently of each other.
