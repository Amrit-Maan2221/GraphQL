# 1️⃣ What a Mutation Really Is

> In GraphQL, a **Mutation is like a command**: “Create, update, or delete something.”

REST analogy:

* POST → create
* PUT/PATCH → update
* DELETE → delete

GraphQL wraps all of this under **mutations**, but still **client decides the response fields**.

---

# 2️⃣ Basic Mutation Structure

```graphql
mutation {
  createUser(input: { name: "Amrit", email: "amrit@example.com" }) {
    id
    name
    email
  }
}
```

**Breakdown:**

* `mutation` → keyword signaling write operation
* `createUser` → field name representing the mutation
* `input` → argument (usually an object type)
* `{ id name email }` → **selection set**, only return what frontend wants

✅ Key senior insight: The **response structure is still client-defined**. Unlike REST, server doesn’t force you to return everything.

---

# 3️⃣ Input Types

Mutations usually accept **input types**, which are structured objects defined in the schema:

```graphql
input CreateUserInput {
  name: String!
  email: String!
}

type Mutation {
  createUser(input: CreateUserInput!): User
}
```

* Input types = strong typing + validation
* Prevents messy argument lists
* Makes schema **self-documenting**

---

# 4️⃣ Updating Data

Mutation for update:

```graphql
mutation {
  updateUser(id: 101, input: { email: "newemail@example.com" }) {
    id
    name
    email
  }
}
```

* Arguments: `id` + `input`
* Returns exactly what the frontend needs

✅ Senior insight: Always return **updated object**, not just a success boolean. Helps frontend update its cache efficiently.

---

# 5️⃣ Deleting Data

```graphql
mutation {
  deleteUser(id: 101) {
    success
    message
  }
}
```

* Delete can return `success` or the deleted object
* Allows **atomic operations**: delete + return status in one request

---

# 6️⃣ Nested Mutations

Sometimes you want multiple writes in one mutation:

```graphql
mutation {
  createUser(input: { name: "Amrit", email: "a@example.com" }) {
    id
    name
  }
  createVehicle(input: { userId: 101, plateNumber: "ABC123" }) {
    id
    plateNumber
  }
}
```

* GraphQL allows multiple mutations in **one request**
* But **execution order matters** if later mutation depends on the first

---

# 7️⃣ Variables in Mutations

Always use variables for dynamic data:

```graphql
mutation CreateUser($input: CreateUserInput!) {
  createUser(input: $input) {
    id
    name
    email
  }
}
```

Variables payload:

```json
{
  "input": { "name": "Amrit", "email": "amrit@example.com" }
}
```

✅ Clean, reusable, secure

---

# 8️⃣ Senior-Level Caveats

* **Mutations are sequential** by default — order matters
* **Resolvers must handle transactions** if multiple fields are written to DB
* Avoid overfetching in mutation response — only return fields needed to update frontend cache
* GraphQL doesn’t enforce **atomicity**, backend must handle it

---

# ⚡ TL;DR – Mutations

1. Mutations = **write operations**
2. Use **input types** for structured arguments
3. Return **exact data needed** for frontend
4. Can chain multiple mutations, but backend must handle dependencies
5. Variables = dynamic, reusable, safe
6. Execution = sequential, field-level resolvers
7. Backend responsibility: **atomicity & validation**
